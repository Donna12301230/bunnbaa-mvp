# BunnBaa 飯飽｜第一階段技術規格

Oct 1, 2026 · @Tom

## 1. 概述

飯飽第一階段做「學生與上班族的餐點預購」（早餐、午餐、晚餐）：消費者提前預訂，越早訂折扣越多，並可轉讓；店家依確定訂單採購備料。成長獎勵、配菜許願、愛心餐三個機制串起回購、需求探索與減少浪費。標語「越早訂，越開心。」

| 角色 | 主要功能 |
| --- | --- |
| 消費者 | 預訂單點或計畫（早鳥折扣）、點圖自組便當（飯量、主菜、配菜）、候選菜許願、搜尋、我的最愛、轉讓／贈送、QR 取餐、抽獎、愛心餐預約 |
| 店家 | 菜單與配方（原料自訂計量單位）、採購與備料清單、流程建議、取餐掃碼、收益看板、券負債看板、訂單統計報表 |
| 平台管理者 | 全域參數、菜色庫與模板、異常審核、天災事件 |

**第一階段範圍**：早／中／晚三個餐期（店家自選供應哪些）、只做自取、週一至週五營業、平台統一規則與單一回饋比例。

**技術棧**：React + TypeScript + Vite 前端；Firebase（Firestore、Functions、Auth）後端；金流 LINE Pay（Request／Confirm／Refund API）；Gemini agent 負責配方草稿、菜名歸類與說明文字。**數量與時間一律由程式計算，AI 不參與任何份量、金額、抽獎的運算。**

**資料主線**：配方 → 自動標籤 → 口味統計 → 候選菜許願 → 進入備料 → 完成取餐 → 計入成長獎勵 → 店家收益看板。

**商業模式**：第一階段平台不抽成，只向店家收取每月維護費 NT$ 1,999（含稅：平台實收 1,904 元、營業稅 95 元），每月開立電子發票；訂單金額全數歸店家（扣除 LINE Pay 手續費）。

- **首月免費**：自店家第一次上架當天起算 30 天，之後每 30 天為一期。
- **繳費**：信用卡定期扣款，或銀行轉帳（虛擬帳號）。
- **逾期**：寬限 7 天並每天提醒；仍未繳則暫停接新訂單，已成立訂單照常出餐，繳清後立即恢復。

## 3. 菜單、模板與配方

店家從定式模板開店，配方分三層：品項 → 半成品 → 原物料。配方同時產生備料數量、成本、份量級距與口味標籤。

### 3.1 定式菜單模板

| 模板 | 結構 |
| --- | --- |
| 經典便當 | 白飯 + 主菜 + 3 配菜 + 滷蛋 |
| 健康餐盒 | 糙米或五穀飯 + 主蛋白 + 4 配菜 |
| 素食便當 | 白飯 + 素主菜 + 3 配菜 |
| 丼飯 | 白飯 + 主菜 + 1 配菜 |
| 麵食 | 麵 + 湯底 + 配料 |

每個模板內含：配菜結構與類別、預設配方、製程資料、3 道候選菜建議、自動標籤。另提供「週菜單輪替」模板（主菜週一至週五輪替）。店家輸入新菜名時，Gemini 產生配方草稿，店家修改數字後儲存。

### 3.2 配方結構

- **供應餐期**：每個品項設定供應的餐期（早／中／晚，可多選）與每個餐期的取餐時段；首頁依此分類。
- **品項類型**：「便當」可自組；「單品」直接點選、不需組合（例如鹹粥、蛋餅、米漿）。
- **便當品項**：由「白飯 + 主菜 + 配菜」組成，每道菜都要有照片（消費者點圖片選菜，見 4.2）。
  - 白飯：半碗／一碗（預設）／一碗半。
  - 主菜：可列多道，每道各自定價（例如雞肉 50、豬肉 60），便當價格以所選主菜為基準。
  - 配菜：店家設定標準配菜數（例如 3 道）與當天可選的配菜；標準數量為預設菜，其餘為候選菜；消費者最多選 4 道，第四道可選「備案」或「加菜」。
- **半成品**：每份用量（以計量單位表示，例如「茄子 80 克」「豬肉 2 片」）、製程時間、設備與容量、可提前製作時間。
- **原物料**：計量單位、熟成率、損耗率、採購單位、保存天數、採購頻率、供應商、最新單價。

**計量單位**：店家為每項原物料自訂單位（克、片、顆、塊、毫升等），並設定「1 採購單位 = 多少計量單位」（例如 1 盒蛋 = 10 顆、1 公斤豬肉片 ≈ 25 片）。配方、材料總和、每日備料與週叫貨單都用同一單位計算，叫貨時再進位成採購單位。以片、顆計的原物料，熟成率與損耗率可設為 1。

原物料用量換算：

```latex
\text{生料用量} = \frac{\text{熟重} \times \text{份數}}{\text{熟成率} \times (1 - \text{損耗率})}
```

單價由店家於每次進貨時更新。

### 3.3 份量級距（成本平衡）

候選菜不加價，改以份量平衡成本，由系統計算、店家可微調。

```latex
\text{份量比例} = \frac{\text{預設菜單份成本}}{\text{候選菜單份成本}}
```

比例 ≥ 0.75 為全份；0.5–0.75 為半份；低於 0.5 不得列為候選。配菜卡片標示級距，例如「筊白筍（半份）」。截單後份量鎖定。

### 3.4 自動標籤

由配方推導：主蛋白（雞、豬、牛、海鮮、素）、烹調方式（炸、滷、烤、炒、蒸）、口味（辣、清淡、甜）、菜類（葉菜、根莖、瓜類）。

## 4. 訂單

消費者最晚在取餐前一天 20:00 下單，以 LINE Pay 付款；截單後不可退款，但仍可轉讓、贈送或捐為愛心餐。

### 4.1 下單與截單

- 最遠可預訂 30 天後的取餐日；鼓勵週六 12:00 前訂好下週，提高週進料準確度。
- **早鳥折扣**：依下單日到取餐日的天數，打在品項原價上（自組便當以所選主菜價格為原價）。提前 14 天以上 7 折列為後續改版目標，級距表預留第三階。

| 提前天數 | 折扣 |
| --- | --- |
| 明天（提前 1 天） | 95 折 |
| 提前 2–30 天 | 8 折 |

- 截單為前一天 20:00，最快只能訂明天。加減選項與折價券在折扣後計算；金額一律由伺服器重算。
- 截單前可自由修改（主菜、配菜、飯量、取餐時段）或取消，LINE Pay 全額退款、折價券退回。
- 截單後不可退款；天災例外見第 11 節。

**轉讓與贈送**：截單前後都可在「轉讓市集」上架轉售，或以連結贈送。取餐時段內可主動「捐為愛心餐」。

- **付費接手**：接手價＝早鳥價＋加減（折價券前），不能自訂。接手者以 LINE Pay 付款後成為新持有人，原付款人自動退回他實付的金額（部分退款）；原付款人用掉的折價券不退回。店家同一份餐只收一次錢。
- **搶單**：按「付款接手」時保留這份 15 分鐘，其他人暫時不能接手；付款失敗則退回賣家。
- **抽獎券**：歸實際付款的人，付費接手後改歸接手者。
- **逾時**：取餐時段結束仍沒人接手，開放 $0 免費領取，原付款人不退款。
- **贈送**：不經付款，抽獎券仍歸原付款人。

### 4.2 自組便當（點圖片選菜）

品項頁以「點圖片」組合便當，一次點擊就完成選擇，不用下拉選單。

| 區塊 | 呈現方式 | 選法 | 價格 |
| --- | --- | --- | --- |
| 白飯 | 三個按鈕「半碗｜一碗｜一碗半」 | 單選，預設一碗 | −5／0／+10 |
| 主菜 | 圖片卡片（菜名＋價格） | 單選，必選 | 依主菜定價，例如 50／60 |
| 配菜 | 圖片卡片（菜名＋份量級距＋許願人數） | 複選，最多 4 道；預設菜已選好 | 少一道 −5；第四道加菜 +10、備案 0 |

- **點選**：點圖片即選取（加框、打勾），再點一次取消。選滿 4 道時其餘卡片變淡。
- **第四道：備案或加菜**：選滿標準數量後再點第 4 道，跳出小視窗二選一。
  - **備案（不加價）**：平常不放進便當；前三道任一道沒供應、已滿或許願未成立時，自動遞補。
  - **加菜 +10**：四道都放進便當。
- **沒有可以換**：已滿或今日未供應的卡片顯示灰色、不能點，改點其他配菜或設備案。
- **材料總和**：底部固定一條「合計 NT$ XX（已含早鳥 8 折）」，點開列出每項材料與份量（例如「白飯 半碗 · 雞腿 1 塊 · 茄子 80 克 · 苦瓜 60 克 · 辣炒年糕 4 塊」）及原價、折扣、應付金額；與店家每日備料使用同一份配方。
- 少選的配菜計入口味統計，作為負面訊號。

### 4.3 候選菜許願

候選菜由店家決定；消費者點選就是一次許願，選的人越多，店家就多備。

1. 卡片直接寫出成立條件，例如「苦瓜（7/10 人，滿 10 人成立）」，並標示份量級距。
2. 候選菜設有本週供應上限，達上限顯示「已滿」。
3. 截單時判定：達最低量者拿到許願菜；未達者有備案換備案，沒有則換回預設菜，並推播「苦瓜這次差 3 人未成立，已幫你換回茄子」。
4. 預設菜照做，不因許願而取消。

### 4.4 計畫（方案）

- 店家設定連續 N 天的計畫（例如 A 方案五日、B 方案七日），下單時選第一天，遇公休自動順延。
- 每一天是獨立的 `locks`，早鳥依各自天數計算，可個別轉讓、贈送或捐出。
- **取餐時段**：下單時只選一個時段套用每一天；要改某一天到「我的餐點」修改，截單前都可以改。
- **點選時先告知**：列出每天日期與價格（順延的標示「順延」）、「所有天數同一時段，之後可個別修改」、取消規則；確認後才付款。

### 4.5 前台介面

**導覽列**：預購餐點、我的餐點、我的最愛、成長獎勵，共四個。「商家」拿掉；「轉讓・愛心餐」併入「我的餐點」，頁上方有「轉讓市集」「附近愛心餐」分頁。

**預購餐點**

- 第一排餐期按鈕「早餐｜午餐｜晚餐」（預設午餐，無供應的變灰）。
- 第二排「單點｜方案」兩個獨立頁面。
- 店家卡片：「看店家」藍色連結；標章旁加愛心收藏按鈕；「看店家」前顯示「再 X 元開獎」。
- 首頁不再放成長獎勵側欄。

**搜尋**：頂部搜尋列可搜店家名稱、菜名、料理類型；結果分「單點」「方案」兩組，只搜目前可預購的品項。

**價格日期列**：全站選日期只用這一種方式。

- 最上方折扣按鈕「95 折｜8 折」，點了跳到該折扣的日期。
- 下方橫向排列明天起 30 天，每天標出當天價格（例如「10/05（一）$72」），顏色區分折扣，公休日灰色。
- 點日期即選定。

**我的最愛**：收藏的店家依收藏時間排序，顯示可預購品項與計畫；僅本人可讀，計入口味偏好正面訊號。

## 5. 採購與備料

店家一週採購一次，系統只分兩區：每週進料與每日備料。米、油、調味料、乾貨與包材等久放品項也併入每週進料，低於安全庫存才列入叫貨單。

| 區塊 | 產生時間 | 內容 | 輸出 |
| --- | --- | --- | --- |
| 每週進料 | 週六 12:00 | 冷凍肉、蛋、根莖類、豆製品、葉菜；米、油、調味料、乾貨、包材（低於安全庫存才叫） | 週叫貨單（含分日到貨） |
| 每日備料 | 前一天 20:05 | 當日半成品份數、流程時間軸、出餐標籤 | 備料任務清單 |

### 5.1 週進料計算

```latex
\text{進料量} = \text{已確定用量} + \text{預測用量} \times 1.1 - \text{目前庫存}
```

- **預測**：過去 4 週同星期幾平均份數（依餐期分開），排除停班日、國定假日與異常週；新店家前 4 週用自填預估。
- **盤點**：週六 12:00 前完成；店家只改有差異的項目，未盤點則以理論庫存計算並標示「未盤點」。
- **採購單位進位**：先以計量單位加總（例如雞蛋 38 顆、豬肉 52 片），再進位成盒、公斤等採購單位。
- **分日到貨**：叫貨單以「原物料 × 週一至週五」呈現，分「已確定」與「預測」；保存 ≤ 3 天的葉菜類建議分批到貨。可一鍵透過 LINE 或 PDF 發給小盤商。

### 5.2 每日備料與流程建議

截單後產生：缺料警示、半成品任務清單（勾選完成）、流程時間軸。時間軸依每個餐期的取餐開始時間分別往回推（早餐 07:30 取餐可能 05:30 開工），同一天多個餐期共用設備容量。範例（午餐 11:00 取餐）：

| 時間 | 任務 |
| --- | --- |
| 前一晚 | 滷雞腿 38 支、滷蛋 40 顆 |
| 08:30 | 洗米浸泡（第 1 鍋 10 杯） |
| 09:00 | 煮飯第 1 鍋；切菜 |
| 09:40 | 煮飯第 2 鍋 |
| 10:00 | 炒玉米炒肉 |
| 10:20 | 炒小白菜、地瓜葉（許願成立） |
| 10:40 | 裝盒、貼出餐標籤 |

排程為確定性演算法（倒推 + 設備容量貪婪分配）；Gemini 只把結果轉成口語提示。時間軸的工時也用於收益看板的備料人工（第 9 節）。

## 6. 取餐

消費者出示 QR code、店家以手機網頁掃碼完成取餐；掃碼是營業額、抽獎券與折價券兌現的觸發點。

1. 消費者開啟訂單頁，顯示取餐 QR code。
2. 店家以網頁相機掃碼（免安裝 App），只有該店家帳號可核銷。
3. 畫面顯示取餐號、主菜、實際配菜（許願與備案結果）、加減選項、折價券折抵、實付金額。
4. 店家按「完成取餐」，觸發 `onOrderCompleted`。

- **安全**：QR code 為伺服器簽章的一次性憑證（訂單 ID + 到期時間 + HMAC），截圖重複使用或偽造皆無效。
- **備援**：4 碼取餐號 + 手機末三碼，由店家在訂單列表手動核對。
- **出餐標籤**：截單後產生，每盒一張：取餐號、配菜內容、加減選項。**不印姓名**（可能轉為愛心餐）。
- **代領**：消費者可分享取餐連結給代領人；店家掃碼畫面支援連續掃描多筆。

## 7. 未取餐與愛心餐

取餐時段結束 30 分鐘後仍未取餐的餐點轉為愛心餐，時段結束 2 小時後報廢；早、中、晚餐期各自計算。原消費者不退款，但照常拿抽獎券。

時間軸（午餐取餐 11:00–13:00 為例）：

| 時間 | 事件 |
| --- | --- |
| 12:30 | 推播提醒尚未取餐者 |
| 13:00 | 取餐時段結束 |
| 13:30 | 未取餐轉愛心餐，開放預約與現場領取 |
| 15:00 | 愛心餐截止，店家輸入送出份數，其餘報廢 |

- 未取餐訂單不退款、計入店家營業額、發放抽獎券。
- 消費者可在取餐時段內主動按「捐為愛心餐」，該份立即開放領取。
- 入口在「我的餐點」的「附近愛心餐」分頁。

### 領取方式

- **線上預約**：手機驗證帳號，每人每天限 1 份；預約後 **10 分鐘內**到場出示 QR code（取餐點多在學校、辦公室附近）。逾時自動釋出給下一位，**不停權**；畫面顯示倒數。
- **現場領取**：未被預約的份數先到先領、不需帳號，每人一份由店家判斷。
- 店家於截止時輸入現場送出份數，其餘記為報廢，報廢份數用於修正下週預測。

### 附近愛心餐

- 位置：目前位置（需授權）或常用地點；距離 500 公尺、1 公里（預設）、2 公里、3 公里。
- 依距離排序，顯示剩餘份數、截止時間、步行時間；來不及的標示「來不及」。
- 「附近有愛心餐」推播預設關閉，開啟後每天最多 2 則。

### 通知文案

主動捐出者（計入個人愛心紀錄）：

> 謝謝你的愛心，你捐出的便當已開放給需要的人領取。

未取餐者（不計入愛心紀錄）：

> 今天的便當沒有領到。為了不浪費，店家已將它轉為愛心餐，開放給需要的人。這筆訂單的抽獎券已照常發放。下次來不了的話，可以在取餐前按「捐為愛心餐」，餐點會更新鮮。

用詞為「已開放領取」，不宣稱「已送到」。若當日沒有報廢，補發「今天的愛心餐都送出去了」給原訂購人（每天一次）。

## 8. 成長獎勵

每週以店家淨營業額的 10% 生成回饋池，拆成折價券供消費者抽獎，人人有獎；抽獎券未達 100 張不開池，持續累積。回饋池以早鳥折扣後的實付金額計算。

### 8.1 結算與開池

- 結算期：週一至週日；週一 00:10 結算上一週。
- 淨營業額：已完成取餐或轉愛心餐的實付金額，扣除退款；開池後的退款從下一期扣除。
- 抽獎券 ≥ 100 張才開池，**不設強制開池**；前台在店家卡片「看店家」前與成長獎勵頁顯示「再 X 元開獎」。
- 回饋池 P = floor(淨營業額 × 10%)。

### 8.2 抽獎券發放

- 以「使用者 × 店家 × 結算期」累計實付金額，每 100 元一張，餘額結轉下一期。
- 發放時機：掃碼完成取餐，或轉為愛心餐時；歸付款人（`payer_uid`，付費接手後為接手者）。
- 只能抽該店家的回饋池；開池前不過期。

### 8.3 券種

第一階段只保留 3 種；一折、三折、八折券列入後續改版。前台以「折 N 元」為主標。

| 等級 | 代碼 | 折抵（元） | 升級成本（元） | 升級權重 |
| --- | --- | --- | --- | --- |
| 免費餐券 | free | 100 | 95 | 30% |
| 半價券 | t50 | 50 | 45 | 70% |
| 九五折券（保底） | t95 | 5 | — | — |

限制：保底折抵 ≤ 100 × 回饋比例，才能人人有獎。

### 8.4 分配演算法

1. 每張抽獎券先配一張保底券：成本 N × 5。
2. 升級預算 B = P − N × 5。
3. 各等級升級張數 = floor(B × 權重 ÷ 升級成本)。
4. 頭獎保證：免費餐券為 0 且剩餘預算 ≥ 95 時，先配 1 張。
5. 剩餘預算繼續升級半價券，直到不足 45。
6. 保底張數 = N − 高階張數；未分配餘額回歸店家。

範例：淨營業額 100,000、P = 10,000、N = 1,000 → B = 5,000；免費餐 15 張、半價 77 張，剩餘 110 再升級半價 2 張 → 半價 79、保底 906，合計 9,980 元，餘 20 元回歸店家。

### 8.5 抽獎

- 開池後 7 天內可抽，逾期未抽的獎項回歸店家。
- 後端於 Firestore Transaction 內執行不放回抽樣：依各等級剩餘張數加權隨機。

## 9. 折價券、商家控管與收益看板

折價券於線上結帳時自動套用，店家不需人工收券；券發出後規則不可變更。店家後台首頁第一張卡片是「本月收益看板」。

### 9.1 折價券使用規則

- 抽中後 30 天有效，領取時明示到期日；到期前 3 天推播提醒。
- 每筆訂單限用一張；折抵 = min(券面折抵, 訂單小計)；不找零、不累積。
- 只能在發券店家使用，綁定帳號、不可轉讓。
- 用券訂單於截單前取消：券退回並保留原到期日。

| 狀態 | 說明 | 下一步 |
| --- | --- | --- |
| issued | 已生成，在池中 | 被抽中 → owned；抽獎期結束 → unclaimed |
| owned | 持有中 | 使用 → redeemed；逾期 → expired |
| redeemed | 已兌現 | 訂單取消 → owned |
| expired | 過期，回歸店家 | — |
| unclaimed | 未被抽，回歸店家 | — |

### 9.2 券負債看板與控管

- 指標：本期回饋池、流通中負債（owned 券折抵總額）、已兌現、回歸金額、未來 7 天到期、距離開池；可匯出 CSV。
- 店家可暫停參加下一期（提前 7 天通知）、查詢單張券；不可修改已發出券的規則。
- 異常偵測（只標記不處分）：7 天內退款 ≥ 3 筆；單一使用者抽獎券占該期 > 20%；同一裝置 > 2 個帳號領券。
- 對帳：每筆訂單記錄原價、加減、折抵、實付金額、券 ID。平台不抽成，只收每月維護費。

### 9.3 本月收益看板

一眼看出本月要備多少材料、扣掉人工後能淨賺多少。

| 指標 | 計算方式 |
| --- | --- |
| 本月營收（已確定） | 本月取餐日、已付款訂單的實付金額合計 |
| 本月營收（預估） | 已確定 + 未下單日期的預測份數 × 近 4 週平均實付 |
| 預計材料成本 | Σ（每份原物料用量 × 份數 × 最新單價）＋包材 |
| 備料人工 | 流程時間軸工時 × 時薪（預設基本工資，只能調高） |
| LINE Pay 手續費 | 實付金額 × 店家合約費率（約 2–3%） |
| 平台維護費 | NT$ 1,999（含稅；首月 0） |
| 員工固定薪資（選填） | 正職月薪，不得低於基本工資月薪 |
| 其他固定成本（選填） | 房租、水電等 |
| **預估淨利** | 營收 − 材料 − 人工 − 手續費 − 維護費 − 薪資 − 其他固定成本 |
| 老闆實際時薪 | 預估淨利 ÷ 老闆本月工時（老闆時間不列成本） |

- 回饋池不另扣：折價券已反映在實付金額。
- 同卡片顯示本月預計備料清單前 10 項。
- **每份毛利**：8 折後售價 − 單份材料成本；低於材料成本 30% 標紅。
- **損益兩平**：「本月還要賣幾份才打平固定成本」。
- **依餐期拆分**：可切換早／中／晚。
- **基本工資**：平台自動更新（以勞動部公告為準、於生效日套用）；店家輸入低於基本工資會被擋下，調漲時自動上調並通知；每天的人工用當天生效的標準。
- 預估數字標註「僅供參考」，月底以實際數字結算。

**訂單統計報表**：「每日收入（最近 15 天）」改為折線圖，另加一條「材料成本」折線，兩線之間即為每日毛利。

## 10. 口味偏好

消費者端推算「我喜歡吃什麼」，用於推薦；店家區域洞察延到第二階段。

- 主動設定：愛吃辣、不吃牛、素食等勾選項。
- 行為推算：以菜色標籤加權計數，近期權重較高（30 天半衰期）。
- 訊號強度：候選菜許願 > 購買＝收藏店家 > 瀏覽；少選的配菜為負面訊號。
- 第一版不使用機器學習；過敏資訊只用於本人篩選；愛心餐紀錄不進入統計與推薦。

## 11. 颱風與天災

取餐地點所在縣市宣布停班時，當日早、中、晚訂單自動取消並全額退款。

| 情境 | 觸發 | 系統處理 |
| --- | --- | --- |
| 海上颱風警報 | 中央氣象署警報資料 | 通知店家建議葉菜延後到貨、預設配菜改耐放菜；新訂單加註「可能因颱風取消」 |
| 停班停課 | 人事行政總處資料（縣市別） | 自動取消、全額退款、折價券退回；不計入營業額與抽獎券 |
| 菜價暴漲 | 店家更新單價或天災事件 | 未截單日期份量級距重算；已截單可等值替換配菜並通知 |

- 停班多在前一晚 20:00 後公布，取消流程必須可在截單後觸發。
- 平台管理者可手動建立天災事件作為備援。
- 「天災期間可等值替換配菜」須事先寫入訂購條款；停班日與天災週排除於預測平均之外。

## 12. Firestore 資料結構

訂單沿用 `locks`、品項沿用 `menu_items`、計畫用 `meal_plans`；取餐點獨立成集合，第二階段加入食物櫃不需重構。

```
platformConfig/global            // 第 2 節全域參數
platformConfig/minimumWage       // monthly, hourly, effectiveFrom, source, history[]
platformConfig/growthReward      // rate, ticketUnit, tiers[], minTicketsToOpen
dishLibrary/{dishId}             // 平台標準菜名、類別、標籤
templates/{templateId}           // 定式菜單模板

vendors/{vendorId}
  name, pickupWindow, cutoffTime, status
  fixedCosts, staffSalary, hourlyWage, ownerHoursPerDay, linePayFeeRate
  billing{ firstListedAt, freeUntil, nextDueAt, status: active|grace|suspended }
  /ingredients/{id}      // unit（店家自訂）, purchase_unit_size, 熟成率, 損耗率, 保存天數, 單價
  /components/{id}       // 每份用量, 製程時間, 設備, 可提前時間
  /inventory/{weekId}    // 週盤點
  /purchaseLists/{id}    // type: weekly|daily
  /prepPlans/{date}      // 每日半成品、時間軸、標籤
  /rewardPeriods/{id}    // netRevenue, pool, tickets, allocation
  /revenueForecast/{month} // revenue, materialCost, laborCost, paymentFee, maintenanceFee, netProfit, ownerHourly, breakEvenQty, byMealPeriod{}

menu_items/{id}          // item_type: bento|single, meal_periods[{period, pickup_window}], mains[{dishId, price}], slots[...]
meal_plans/{id}          // 連續天數、順延規則

locks/{lockId}           // 一筆＝一份餐點
  buyer_uid, payer_uid, vendor_id, menu_item_id, pickup_date, pickup_slot
  main_dish_id, slots[...], extra_side{dishId, mode: backup|addon}, rice: add|normal|less
  plan_id, plan_day
  list_price, early_bird_amount, adjust_amount, coupon_discount, locked_price, coupon_id
  paid_amount（付款人實付，退款依據）, resale_hold{uid, intent_id, expires_at}, transfers[], transfer_refund
  status: locked|for_resale|for_gift|fulfilled|resold_and_fulfilled|charity|cancelled

sideWishes/{vendorId}_{date}_{slot}_{dishId}   // 候選菜許願計數
userSpend/{vendorId}_{userId}                  // 累計消費與抽獎券
rewardTickets/{id}  coupons/{id}               // tier: free|t50|t95
tasteProfiles/{userId}                         // 僅本人可讀
users/{userId}/favorites/{vendorId}            // 我的最愛，僅本人可讀寫
charityMeals/{id}  charityReservations/{id}  disasterEvents/{id}  payment_intents/{id}
```

安全規則：`tasteProfiles` 與 `favorites` 僅本人；`charity*` 不開放店家讀個人欄位；抽獎、兌現、開池、基本工資檢查一律由後端寫入。

## 14. 隱私與法規

上線前活動辦法、訂購條款、隱私條款須經律師審閱；以下為設計依據，非法律意見。

- **折價券效期**：無償發行的折價券可設期限，須於領取時明示。
- **抽獎**：屬公平交易法「贈獎」，單張券最高 100 元，遠低於上限。
- **截單後不退款**：現做餐點屬易腐敗商品，條款寫法待律師確認；以轉讓、贈送作為替代。
- **天災**：停班自動退款、等值替換配菜須事先寫入條款。
- **愛心餐**：現場自取、當日有效；食安責任由店家負責。
- **隱私**：店家只看得到取餐號；標籤不印姓名；不存定位軌跡，常用地點只存約 150 公尺 geohash；購買紀錄只用於本人推薦。
