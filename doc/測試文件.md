## 1. 測試環境

### 1.1 兩種環境怎麼選

| 環境 | 用途 | 注意 |
|---|---|---|
| **本機 Emulator**（`VITE_USE_EMULATORS=true`＋`npm run dev:emulator`） | 功能測試、負面測試、規則測試，可以隨便弄壞資料 | ① emulator **不檢查複合索引**，查詢缺索引的 bug 測不出來 ② `assertAdminOrVendorOwner` 在 emulator 直接放行，**權限類測試一定要在正式站再測一次** ③ 種子裡「今天／明天」的訂單過期了就 `npm run dev:emulator:reset` |

### 1.3 外部服務

- **LINE Pay Sandbox**：付款頁按付款即可，不會真的扣款。
- **Gemini**：可能回 503／429。程式有重試，重試用完仍失敗時要看畫面有沒有錯誤提示，不算功能 bug。
  - AI 功能（拍照上架、預購助理、轉讓媒合、預測區間的追問）都會真的呼叫 Gemini，走 Vertex AI（服務帳號認證，不需要 API key）。emulator 要測就移除 `functions/.env.local` 的 `GEMINI_DISABLED`，並用有專案權限的帳號 `gcloud auth application-default login`。
  - 測預購助理時同一句問題 10 分鐘內會回快取（回應帶 `cached: true`），要測真實呼叫就換一句。
- **天災資料**：`pollDisasterFeeds` 抓國家災害防救科技中心 CAP feed（停班停課、颱風警報）。平常抓不到真實事件，測試一律用管理後台「天災事件」手動建立（備援機制本身也要測）。
- **時間相關排程**：截單、轉愛心餐、回饋池結算都跟台北時間綁定。emulator 用各自的 `trigger*Now` 或把測試資料的日期／時段設成「剛好過了」來觸發，不用等真的時間。
- **Firestore 向量搜尋**（轉讓媒合）：正式站要先部署 `menu_embeddings` 向量索引，並由管理員呼叫一次 `backfillMenuEmbeddings`。emulator 若不支援向量搜尋，媒合會退回「訂過同一個品項的人」，相似品項那部分只能在正式站測。
- **FCM 推播**：需要 HTTPS＋瀏覽器允許通知，只能在正式站測。
- **相機**：需要 HTTPS，只能在正式站用手機測（iPhone Safari＋Android Chrome 各一次）。
- **手機 OTP**：本機的 reCAPTCHA 常常失敗，只在正式站用真手機號碼測。

## 測試案例怎麼讀

- **ID**：`區塊-編號`，回報 bug 時引用。
- **優先級**：P0＝Demo 主線，壞了不能 Demo；P1＝重要功能；P2＝邊界或次要。
- **環境**：E＝Emulator 可測；P＝只能在正式站測；E/P＝兩邊都要。
- **結果**：填 `PASS`／`FAIL`／`BLOCKED`＋日期＋測試人，FAIL 附缺陷編號（見第 11 章）。
- **自動化**：結果寫「自動化」的是 `scripts/tests` 跑過：「邏輯層」「規則層」是 `npm test`，「Functions」是 `npm run test:functions` 與 `npm run test:functions:more`（在測試 emulator 上真的呼叫 Cloud Functions；排程類在本機直接執行 handler，見 `scripts/tests/functions.test.js`、`functions-more.test.js` 開頭）。「畫面」是在本機 emulator＋Chrome 實際操作。只驗證伺服器端；括號裡寫還缺哪一段要人工測，補測完再改成一般結果。
- **作廢**：第一階段規格改版後不再適用的舊案例，結果欄已標「作廢（改版）」並註明由哪個案例取代，不用再測；保留 ID 是為了對得上舊的測試紀錄。
- **規格**：「規格 §x」指 [第一階段規格.md](第一階段規格.md) 的章節（1002 版；更早的版本見 git 歷史）。

## 9. 端到端情境（整合測試，TODO §4）

每次 Demo 前在正式站完整跑一次。三條線串在一起，前一步的輸出是下一步的輸入。

### 情境 A：一筆訂單的一生（消費者 → 商家 → 管理員）

1. 會員 A 註冊登入 → 首頁選 3 天後的商品，加入購物車（同一家的兩個品項；另外確認加入第二家會被擋）→ 選時段、填備註 → LINE Pay Sandbox 付款（C-AUTH-01、C-ORD-02）
2. 確認付款成功頁 QR、`/my-bookings` 出現、金額是 8 折（C-PRC-03）
3. 商家店主在「今日備料」、「訂餐時段」、「訂單管理」都看得到這筆與備註（V-PRP-01、V-SES-01、V-ORD-01）
4. 取餐日當天，店主用相機掃會員 QR → 確認取餐（V-RDM-10）
5. 會員打 5 星＋公開心得 → Landing 出現評價（C-MY-11、C-NAV-02）
6. 管理員手動結算 → 撥款總覽出現、商家總覽營收更新（A-PAY-01、F-01）

### 情境 B：轉讓與贈送

1. 會員 A 鎖定兩筆 → 一筆上架轉讓（期限 1 小時）、一筆贈送（C-MY-03、C-MY-05）
2. 會員 B 在市集接手第一筆；開連結領取第二筆（C-MKT-02、C-MY-06）
3. A 的「我的轉讓」看得到兩筆去向；B 的我的餐點有兩筆（C-MY-09）
4. 店主核銷 B 的 QR 成功（V-RDM-04）

### 情境 C：未取餐 → 愛心餐 → 報廢回饋

## 附錄：已知限制（不算 bug）

測到下面這些行為時標 `PASS（已知限制）`，不用開缺陷：

1. 首頁左側時段選擇是所有店共用預設時段，下單時才檢查該店有沒有開這個時段。
2. 2026-09-25 以前的訂單不計入份數。
3. 商家改設定後，消費者要重新整理才看得到，伺服器結帳一律照最新設定。
4. 2026-09-28 以前加入的計畫沒有 `meal_plan_id`，評分只算進店家平均。
5. 轉讓後原持有人可以讀整筆 lock，包含新持有人的回饋。
6. 店名英文與計畫方案英文沒有編輯介面，只能靠自動翻譯或到 Firestore Console 改。
7. Landing「近期活動」沒有後台編輯頁，要到 Firestore Console 改。
8. 贈送沒有「指名」，拿到連結的任何登入者都能領。
9. 預購助理每人每天 30 次；同一句單輪問題 10 分鐘內回快取，名額與價格可能跟最新狀態差幾分鐘（點進品項頁、結帳時會再算）。
10. 轉讓媒合只找「過去訂過相同或相似品項」的會員，新會員不會收到；逾時免費領取走前端規則，不會記 `claimed_by_match`。
11. 預估取餐區間要至少 3 個營業日、每天至少 3 份的紀錄才會顯示。
12. 拍照上架的英文名稱會當成「手動英文」存下，之後只改中文不會自動重翻；要自動翻譯就把英文欄清空。
13. 規格 §13 列的 `applyCoupon`、`onOrderCompleted`／`onOrderRefunded` 在實作裡分別併進結帳（`createCartLinePayReservation`）與 `onLockWritten`，測試照實際名稱。

15. 愛心餐只能說「已開放領取」，第一階段無法追蹤單一盒的去向（規格 §7.4）。

20. 維護費第一階段沒有線上扣款：`billingCycle` 只依訂閱到期日判斷寬限與暫停，繳費後由管理員續約；基本工資由管理員在 `platformConfig/minimumWage` 填勞動部公告，自動抓取待確認（規格 §16）。
