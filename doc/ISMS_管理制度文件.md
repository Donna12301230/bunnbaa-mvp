## 1. 資訊安全政策

**政策聲明**：BunnBaa 在取得使用者信任、保護消費者與商家資料機密性、完整性與可用性的前提下提供服務。任何功能或商業決策，若會犧牲已上線帳號的存取控制、資料完整性規則，或使用者個資保護，都必須先經過資安負責人確認。

**目標**：
- 消費者與商家的個人資料、交易紀錄不因權限設計疏漏而外洩
- 平台管理員／商家帳號的存取權限可追溯（見 `admin_audit_logs`）
- 服務在單一開發者的操作失誤下，不會導致全站資料遺失（見第 6 節備份現況——目前還做不到，是已知缺口）

**政策生效與例外**：本政策由 SU 與 Donna 共同同意後生效。任何偏離本政策的技術決定（例如第 3 節風險登錄表裡「暫時接受」的風險），都必須記錄在對應文件裡並註明理由與重新檢視時間，不能只是沒做。

## 5. 事件應變程序

**分級**：
- **P1（嚴重）**：資料外洩、帳號被盜用、正式站服務中斷
- **P2（中等）**：規則/權限設定錯誤但尚未證實被利用、單一功能異常
- **P3（輕微）**：非安全性的一般 bug

**處理步驟**（P1/P2）：
1. 發現者立即通知另一位夥伴（SU／Donna），不單獨處理
2. 若是帳號被盜：立即在 Firebase Console／GitHub 撤銷該帳號的 session、改密碼
3. 若是規則錯誤：優先部署修正後的 `firestore.rules`（不需要等 Functions 一起，規則可以獨立部署）
4. 查證影響範圍：翻 `admin_audit_logs`、Cloud Audit Logs（若已啟用）、Firebase Auth 登入紀錄
5. 記錄事件：時間、發現方式、影響範圍、處理過程，寫成一個事後報告（暫定存在 repo 的 `incidents/` 目錄，目前還沒發生過事件，這個目錄尚未建立）
6. 需要對外揭露的情況（例如確認個資外洩）：由 Donna 對外溝通，不由工程端片面決定

目前沒有正式的「通報窗口」或客服信箱以外的機制；`herzbaa@gmail.com`（見 `CustomerLayout.tsx` 頁尾）是目前唯一對外聯絡管道。

## 6. 備份與營運持續計畫（現況：尚未建立，這節寫的是缺口與暫行做法）

- **目前沒有 Firestore 排程備份／PITR**。Blaze 已解除，純粹是還沒設定，屬於落差分析 P2 待辦。
- **暫行做法**：`scripts/seed.js` 可以重建一份 demo 資料（不是正式使用者資料的備份）；正式使用者資料目前完全依賴 Google 的基礎設施可用性，沒有 BunnBaa 自己的復原機制。
- **RTO／RPO 目標**（先訂一個粗略目標，之後有備份機制再收斂）：試營運階段可接受 RPO（可容忍的資料遺失量）＝到目前為止沒有備份就是全部；這是不可接受的長期狀態，**正式營運前必須**至少設定每日一次 Firestore 匯出到 Cloud Storage。
- Cloud Functions／Hosting／規則的「備份」等同於 Git 歷史紀錄，這部分沒有問題，隨時可以重新部署任一個 commit 的版本。

## 7. 供應商（第三方處理者）清單

| 供應商 | 用途 | 資料流向 | 備註 |
|---|---|---|---|
| Google Cloud / Firebase | 資料庫、驗證、後端運算、託管 | 幾乎所有使用者與交易資料 | 具 ISO 27001 認證；帳單／專案擁有者為 Donna 的帳號 |
| LINE Pay | 消費端金流 | 訂單金額、交易編號（不經手信用卡卡號，卡號在 LINE Pay 端輸入） | 目前為 Sandbox，正式上線需走特約商店審核（TODO §1） |
| Google Gemini API | 商家校準報告、消費者折扣說明文字生成 | 訂單歷史統計數據（不含個資姓名/電話），生成文字 | API Key 存 `functions/.env`，見風險 R7 |
| Firebase Storage（Google Cloud） | 商家封面圖/菜單圖片上傳（`ImageUploadField.tsx`，規則見 `storage.rules`） | 圖片檔案 | 公開可讀；僅該店店主或管理員可寫，限 image/* 且 ≤ 5MB |

供應商清單由新增第三方服務的人（通常是動到 `functions/.env` 或新增 npm 套件呼叫外部 API 的人）順手更新這裡。

## 8. 人員安全

兩人團隊，沒有僱傭其他工程師或外部承包商。現階段做法：
- 兩人都各自對自己持有的帳號（GCP 擁有者、平台管理員）負保密責任，密碼不透過不安全管道（如純文字訊息）傳遞
- 若團隊擴大、引入新成員或外部協作者，離職／結束合作時要：撤銷其 Firebase Console 存取權、GitHub repo 存取權、若曾知悉任何 API Key／密碼要輪替
- 目前沒有正式的保密協議（NDA）文件，這是規模擴大前需要補的項目
