# BunnBaa 飯飽｜第一階段技術規格

Sep 29, 2026 · @Tom

## 1. 概述

飯飽第一階段做「上班族午餐便當預購」：消費者提前預訂、店家依確定訂單採購備料，並以成長獎勵、配菜許願、愛心餐三個機制串起回購、需求探索與減少浪費。標語「越早訂，越開心。」

**角色**

| 角色 | 主要功能 |
| --- | --- |
| 消費者 | 預訂、加減飯菜、配菜許願、開放許願、QR 取餐、抽獎、愛心餐預約 |
| 店家 | 菜單與配方、採購與備料清單、流程建議、取餐掃碼、券負債看板、區域洞察 |
| 平台管理者 | 全域參數、菜色庫與模板、異常審核、天災事件 |

**第一階段範圍**：只做午餐、只做自取、週一至週五營業、平台統一規則與單一回饋比例。

**技術棧**：React + TypeScript + Vite 前端；Firebase（Firestore、Functions、Auth）後端；Gemini agent 負責配方草稿、菜名歸類與說明文字。**數量與時間一律由程式計算，AI 不參與任何份量、金額、抽獎的運算。**

**資料主線**：配方 → 自動標籤 → 口味統計 → 發現缺口 → 許願 → 進入備料 → 完成取餐 → 計入成長獎勵。

## 3. 菜單、模板與配方

店家從定式模板開店，配方分三層：品項 → 半成品 → 原物料。配方同時產生備料數量、成本、份量級距與口味標籤。

### 3.1 定式菜單模板

| 模板 | 結構 |
| --- | --- |
| 經典便當 | 白飯 + 主菜 + 3 配菜 + 滷蛋 |
| 健康餐盒 | 糙米或五穀飯 + 主蛋白 + 4 配菜 |
| 素食便當 | 白飯 + 素主菜 + 3 配菜 |
| 丼飯 | 白飯 + 主菜 + 1 配菜 |
| 麵食 | 麵 + 湯底 + 配料 |

每個模板內含：配菜格結構與類別、預設配方、製程資料、每格 3 道候選菜建議、自動標籤。另提供「週菜單輪替」模板（主菜週一至週五輪替）。

店家輸入新菜名時，Gemini 產生配方草稿，店家修改數字後儲存。

### 3.2 配方結構

- **品項**：主菜固定一道；配菜格各有一道預設菜與最多 3 道候選菜；每格有類別（青菜類、肉類配菜、蛋豆類等），候選菜只能從同類別挑選。
- **半成品**：每份用量（熟重）、製程時間、設備與容量、可提前製作時間。
- **原物料**：熟成率、損耗率、採購單位（例如蛋以盒計）、保存天數、採購頻率、供應商、最新單價。

原物料用量換算：

```latex
\text{生料用量} = \frac{\text{熟重} \times \text{份數}}{\text{熟成率} \times (1 - \text{損耗率})}
```

單價由店家於每次進貨時更新；之後可評估串接農產品批發行情公開資料作為參考價。

### 3.3 份量級距（成本平衡）

候選菜不加價，改以份量平衡成本，由系統計算、店家可微調，消費者不選級距。

```latex
\text{份量比例} = \frac{\text{預設菜單份成本}}{\text{候選菜單份成本}}
```

比例 ≥ 1 為全份；0.75–1 為 3/4 份；0.5–0.75 為半份；低於 0.5 不得列為該格候選。下拉選單標示級距，例如「筊白筍（半份）」。截單後份量鎖定。

### 3.4 自動標籤

由配方推導：主蛋白（雞、豬、牛、海鮮、素）、烹調方式（炸、滷、烤、炒、蒸）、口味（辣、清淡、甜）、菜類（葉菜、根莖、瓜類）。

## 4. 訂單

消費者最晚在取餐前一天 20:00 下單，截單後不可免費取消；配菜可許願，未成立自動退回預設菜，訂單照常成立。

### 4.1 下單與截單

- 可預訂至下週五；鼓勵週六 12:00 前訂好下週，以提高週進料準確度。
- 截單前可自由修改或取消，全額退款。
- 截單後不可免費取消（店家已依訂單備料）；天災例外見第 11 節。

### 4.2 加減選項

| 選項 | 價格 | 備料影響 |
| --- | --- | --- |
| 加飯 | +10 | 多一份白飯，每份限一次 |
| 減飯 | −5 | 白飯減半 |
| 某格配菜不要 | 每格 −5 | 該格不備 |

- 主菜不可減。
- 加減於下單時直接反映在訂單金額，不走退款。
- 選「不要」的格子不能許願。
- 「不要」計入口味統計，作為負面訊號。

### 4.3 配菜許願（候選菜）

1. 每格顯示預設菜，下拉選單列出候選菜，標示份量級距與進度（例如「地瓜葉 7/10」）。
2. 候選菜設有本週供應上限，依週進料庫存計算，達上限顯示「已滿」。
3. 截單時判定：達最低量者，許願的人拿到許願菜；未達者自動改為預設菜，並推播通知。
4. 預設菜照做，不因許願而取消。

### 4.4 開放許願（參考名單）

- 消費者可許願店家未提供的菜：先從平台菜色庫選，找不到再自由輸入，由 Gemini 歸類到標準菜名。
- 以人數計，同一人重複許願只算一次；只計近 30 天。
- 達 20 人通知店家列入參考名單，店家自行決定是否上架；上架時 Gemini 產生配方草稿。
- 上架後通知當初許願的人。畫面註明「許願不保證供應」。

## 5. 採購與備料

店家一週採購一次，系統分三區：每月備料（小盤商）、本週進料（週六 12:00 鎖定，可分日到貨）、每日備料（截單後產生）。每個原物料依「採購頻率」自動歸區。

### 5.1 三區分工

| 區塊 | 產生時間 | 內容 | 輸出 |
| --- | --- | --- | --- |
| 每月備料 | 每月 25 日 | 米、油、調味料、乾貨、便當盒與包材 | 小盤商叫貨單 |
| 本週進料 | 週六 12:00 | 冷凍肉、蛋、根莖類、豆製品、葉菜 | 週叫貨單（含分日到貨） |
| 每日備料 | 前一天 20:05 | 當日半成品份數、流程時間軸、出餐標籤 | 備料任務清單 |

### 5.2 週進料計算

```latex
\text{進料量} = \text{已確定用量} + \text{預測用量} \times 1.1 - \text{目前庫存}
```

- **預測**：過去 4 週同星期幾平均份數，排除停班日、國定假日與店家標記的異常週；新店家前 4 週使用店家自填預估。
- **盤點**：週六 12:00 前完成。系統列出理論剩餘量，店家只改有差異的項目；未盤點則以理論庫存計算並標示「未盤點」。
- **採購單位進位**：例如蛋以盒、肉以公斤為單位。

### 5.3 未來訂單看板與分日到貨

週叫貨單以「原物料 × 週一至週五」呈現，每格分「已確定」與「預測」兩部分，越接近當天已確定比例越高。保存天數 ≤ 3 天的原物料（葉菜類）自動建議分批到貨，例如週一、週三各送一次；冷凍與乾貨一次進。叫貨單可一鍵透過 LINE 或 PDF 發給小盤商。

### 5.4 每日備料與流程建議

截單後產生：

- **採購差額與缺料警示**：當日需求超過週庫存時立即提醒臨時補貨。
- **半成品任務清單**：遊戲化勾選，完成一項勾一項。
- **流程時間軸**：從取餐開始時間往回推排程，依製程時間、設備容量、可提前時間計算。範例（取餐 11:00）：

| 時間 | 任務 |
| --- | --- |
| 前一晚 | 滷雞腿 38 支、滷蛋 40 顆 |
| 08:30 | 洗米浸泡（第 1 鍋 10 杯） |
| 09:00 | 煮飯第 1 鍋；切菜 |
| 09:40 | 煮飯第 2 鍋 |
| 10:00 | 炒玉米炒肉 |
| 10:20 | 炒小白菜、地瓜葉（許願成立） |
| 10:40 | 裝盒、貼出餐標籤 |

排程為確定性演算法（倒推 + 設備容量貪婪分配），不使用 AI 計算；Gemini 只負責把結果轉成口語提示。

## 6. 取餐

消費者出示 QR code、店家以手機網頁掃碼完成取餐；掃碼是營業額、抽獎券與折價券兌現的觸發點。

### 6.1 流程

1. 消費者開啟訂單頁，顯示取餐 QR code。
2. 店家以網頁相機掃碼（免安裝 App），只有該店家帳號可核銷。
3. 畫面顯示取餐號、主菜、實際配菜（許願結果）、加減選項、折價券折抵、實付金額。
4. 店家按「完成取餐」，觸發 `onOrderCompleted`。

### 6.2 安全與備援

- QR code 內容為伺服器簽章的一次性憑證（訂單 ID + 到期時間 + HMAC），截圖重複使用或偽造皆無效。
- 備援：4 碼取餐號 + 手機末三碼，由店家在訂單列表手動核對。

### 6.3 出餐標籤

截單後產生可列印的標籤清單，每盒一張：取餐號、配菜內容、加減選項。**標籤不印姓名**（便當可能轉為愛心餐）。

### 6.4 代領

消費者可將取餐連結分享給代領人；店家掃碼畫面支援連續掃描多筆。

## 7. 未取餐與愛心餐

取餐時段結束 30 分鐘後仍未取餐的便當轉為愛心餐，當天現場領取，時段結束 2 小時後報廢；原消費者不退款，但照常拿抽獎券。

### 7.1 時間軸（取餐 11:00–13:00 為例）

| 時間 | 事件 |
| --- | --- |
| 12:30 | 推播提醒尚未取餐者 |
| 13:00 | 取餐時段結束 |
| 13:30 | 未取餐轉愛心餐，開放預約與現場領取 |
| 15:00 | 愛心餐截止，店家輸入送出份數，其餘報廢 |

- 未取餐訂單：不退款、計入店家營業額、發放抽獎券。
- 消費者可在取餐時段內主動按「捐為愛心餐」，該份立即開放領取。

### 7.2 領取方式

- **線上預約**：手機驗證帳號，每人每天限 1 份；預約後 30 分鐘內到場出示 QR code，店家掃碼確認。逾時未到，該份釋出並停止預約功能 7 天（不影響一般訂餐）。預約前畫面清楚提示懲罰規則。
- **現場領取**：未被預約的份數先到先領、不需帳號，每人一份由店家現場判斷。
- 店家於 15:00 輸入現場送出份數，其餘記為報廢。

### 7.3 附近愛心餐

- 位置來源：目前位置（需授權）或常用地點。
- 距離可調：500 公尺、1 公里（預設）、2 公里、3 公里。
- 依距離排序，顯示剩餘份數、截止時間、步行時間；步行時間超過剩餘時間者標示「來不及」。
- 「附近有愛心餐」推播預設關閉，開啟後只在愛心餐時段、範圍內推播，每天最多 2 則。

### 7.4 通知文案

主動捐出者（計入個人愛心紀錄）：

> 謝謝你的愛心 你捐出的便當已開放給需要的人領取。

未取餐者（不計入愛心紀錄）：

> 今天的便當沒有領到 為了不浪費，店家已將它轉為愛心餐，開放給需要的人。這筆訂單的抽獎券已照常發放。 下次來不了的話，可以在取餐前按「捐為愛心餐」，餐點會更新鮮。

用詞為「已開放領取」，不宣稱「已送到」，因為第一階段無法追蹤單一盒的去向。當日愛心餐全數送出時，可補發「今天的愛心餐都送出去了」。使用者可在設定中關閉愛心餐通知。

### 7.5 報廢回饋

報廢份數顯示於店家後台，並用於修正下週預測。

## 8. 成長獎勵

每週以店家淨營業額的 10% 生成回饋池，拆成折價券供消費者抽獎，人人有獎；抽獎券未達 100 張不開池，持續累積直到達標。

### 8.1 結算與開池

- 結算期：週一至週日；週一 00:10 結算上一週。
- 淨營業額：已完成取餐或轉愛心餐的訂單實付金額，扣除退款；開池後才發生的退款從下一期扣除（可負數結轉）。
- 抽獎券總數 ≥ 100 張才開池；未達標則營業額與抽獎券累積到下一期，**不設強制開池**。前台顯示「再 X 元開獎」。
- 回饋池 P = floor(淨營業額 × 10%)。

### 8.2 抽獎券發放

- 以「使用者 × 店家 × 結算期」累計實付金額，每 100 元一張，餘額結轉下一期。
- 發放時機：掃碼完成取餐，或訂單轉為愛心餐時。
- 抽獎券只能抽該店家的回饋池；開池前不過期。

### 8.3 券種

每張折價券以 100 元為單位，前台以「折 N 元」為主標、「（百元一折）」為副標。

| 等級 | 代碼 | 折抵 | 升級成本 | 升級權重 |
| --- | --- | --- | --- | --- |
| 零元券 | free | 100 | 95 | 5% |
| 一折券 | t10 | 90 | 85 | 10% |
| 三折券 | t30 | 70 | 65 | 15% |
| 五折券 | t50 | 50 | 45 | 25% |
| 八折券 | t80 | 20 | 15 | 45% |
| 九五折券（保底） | t95 | 5 | — | — |

限制：保底折抵 ≤ 100 × 回饋比例，才能人人有獎。

### 8.4 分配演算法

1. 每張抽獎券先配一張保底券：成本 N × 5。
2. 升級預算 B = P − N × 5。
3. 各等級升級張數 = floor(B × 權重 ÷ 升級成本)。
4. 頭獎保證：零元券為 0 且剩餘預算 ≥ 95 時，先配 1 張。
5. 剩餘預算繼續升級八折券，直到不足 15。
6. 保底張數 = N − 高階張數；未分配餘額回歸店家。

範例：淨營業額 100,000、P = 10,000、N = 1,000 → 零元 2、一折 5、三折 11、五折 27、八折 163、保底 792，合計 9,990 元，餘 10 元回歸店家。

### 8.5 抽獎

- 開池後 7 天內可抽，逾期未抽的獎項回歸店家。
- 後端 Callable Function 於 Firestore Transaction 內執行不放回抽樣：依各等級剩餘張數加權隨機，抽中後該等級減一。

## 9. 折價券與商家控管

折價券於線上結帳時自動套用，店家不需人工收券；店家後台以「流通中負債」掌握潛在成本，券發出後規則不可變更。

### 9.1 使用規則

- 抽中後 30 天有效，領取時明示到期日；到期前 3 天推播提醒。
- 每筆訂單限用一張；折抵 = min(券面折抵, 加減後訂單小計)；不找零、不累積。
- 只能在發券店家使用，綁定帳號、不可轉讓。
- 用券訂單於截單前取消：券退回並保留原到期日；已過期則不退。
- 用券與未用券的份量與內容必須一致。

### 9.2 狀態

| 狀態 | 說明 | 下一步 |
| --- | --- | --- |
| issued | 已生成，在池中 | 被抽中 → owned；抽獎期結束 → unclaimed |
| owned | 持有中 | 結帳使用 → redeemed；逾期 → expired |
| redeemed | 已兌現 | 訂單取消 → owned |
| expired | 過期，回歸店家 | — |
| unclaimed | 未被抽，回歸店家 | — |

### 9.3 券負債看板

| 指標 | 說明 |
| --- | --- |
| 本期回饋池 | 金額與券種分配 |
| 流通中負債 | owned 狀態券的折抵總額 |
| 已兌現 | 本期與累計的金額、張數 |
| 回歸金額 | 過期、未抽、未分配合計 |
| 預估到期 | 未來 7 天到期的券總額 |
| 距離開池 | 未開池時的累積進度 |

支援依期間匯出 CSV。

### 9.4 店家可操作項目

- 暫停參加下一期：提前 7 天通知，已發出的券照常兌現。
- 以券 ID 或訂單查詢單張券紀錄。
- 不可修改已發出券的折抵、效期或適用範圍。

### 9.5 異常偵測

以下情況標記並通知平台與店家，不自動處分：7 天內退款 ≥ 3 筆；單一使用者抽獎券占該期 > 20%；同一裝置 > 2 個帳號領券。

### 9.6 對帳

每筆訂單記錄原價、加減金額、折抵金額、實付金額、使用券 ID。平台抽成以實付金額計算。

## 10. 口味偏好與區域洞察

消費者端推算「我喜歡吃什麼」；店家端只看得到取餐點周邊的匿名統計與供需缺口，看不到任何個人資料。

### 10.1 消費者偏好

- 主動設定：愛吃辣、不吃牛、素食等勾選項。
- 行為推算：以菜色標籤加權計數，近期訂單權重較高（30 天半衰期），重複購買加權。
- 訊號強度：開放許願 > 候選菜許願 > 購買 > 瀏覽；選「不要」為負面訊號。
- 用途：推薦店家與菜色；第一版不使用機器學習。

### 10.2 店家區域洞察

- 範圍：取餐點方圓 1 公里、近 30 天。
- 統計人數少於 20 人不顯示。
- 呈現：標籤占比（例如雞肉類 42%、辣味 18%）、開放許願排行、「不要」率高的菜、**供需缺口**（需求高但附近供應店家少的標籤）。
- 缺口可一鍵建立候選菜或開放許願試水溫。

### 10.3 排除資料

過敏資訊只用於使用者自己的篩選；愛心餐的預約、領取、瀏覽紀錄一律不進入統計與推薦。

## 11. 颱風與天災

取餐地點所在縣市宣布停班時，當日訂單自動取消並全額退款；颱風警報期間提前預警店家調整採購，天災期間店家可等值替換配菜。

| 情境 | 觸發 | 系統處理 |
| --- | --- | --- |
| 海上颱風警報 | 中央氣象署警報資料 | 通知有訂單的店家：建議葉菜延後到貨、預設配菜暫改耐放菜；受影響日期新訂單加註「可能因颱風取消」 |
| 停班停課 | 人事行政總處停班停課資料（縣市別） | 當日訂單自動取消、全額退款、折價券退回；不計入營業額與抽獎券；平台不收抽成 |
| 菜價暴漲 | 店家更新單價或天災事件 | 未截單日期份量級距自動重算；已截單訂單店家可等值替換配菜並通知消費者 |

- 停班多在前一晚 20:00 後公布，取消流程必須可在截單後觸發。
- 平台管理者可手動建立天災事件，作為資料來源失效時的備援。
- 「天災期間可等值替換配菜」須事先寫入訂購條款。
- 停班日與天災週自動排除於預測平均之外。
- 資料來源格式與更新頻率於開發時確認。

## 12. Firestore 資料結構

以下為主要集合與欄位；取餐點獨立成集合，第二階段加入食物櫃時不需重構。

```
platformConfig/global            // 第 2 節全域參數
platformConfig/growthReward      // rate, ticketUnit, tiers[], minTicketsToOpen ...
dishLibrary/{dishId}             // 平台標準菜名、別名、類別、標籤
templates/{templateId}           // 定式菜單模板

vendors/{vendorId}
  name, pickupWindow, cutoffTime, status
  /ingredients/{ingredientId}    // 原物料：單位、熟成率、損耗率、保存天數、採購頻率、供應商、單價
  /components/{componentId}      // 半成品：配方、製程時間、設備、可提前時間
  /items/{itemId}                // 品項：主菜、slots[{category, defaultDish, candidates[{dishId, portionLevel, weeklyCap, minQty}]}]
  /suppliers/{supplierId}        // 小盤商通訊錄
  /inventory/{weekId}            // 週盤點
  /purchaseLists/{listId}        // type: monthly | weekly | daily，分日到貨明細
  /prepPlans/{date}              // 每日半成品、時間軸、標籤清單
  /rewardPeriods/{periodId}      // status, netRevenue, carried, pool, tickets, allocation, remaining
  /wishTally/{dishId}            // 開放許願人數（近 30 天）

pickupPoints/{pointId}           // type: counter | locker, vendorId, geohash, lockerConfig

orders/{orderId}
  userId, vendorId, pickupPointId, pickupDate
  items[{itemId, slots[{dish, wished, resolved, removed}], rice: add|normal|less}]
  originalAmount, adjustAmount, discountAmount, paidAmount, couponId
  status: placed | locked | completed | charity | cancelled | refunded
  pickupCode, qrNonce

sideWishes/{vendorId}_{date}_{slot}_{dishId}   // 候選菜許願計數
openWishes/{wishId}              // userId, vendorId, dishId, createdAt
userSpend/{vendorId}_{userId}_{periodId}       // cumulative, ticketsIssued, carryOver
rewardTickets/{ticketId}         // status: pending | drawable | drawn | forfeited
coupons/{couponId}               // tier, discount, status, issuedAt, expiresAt, orderId
tasteProfiles/{userId}           // 主動設定 + 標籤分數（僅本人可讀）
areaInsights/{geohash5}_{week}   // 匿名彙總，低於 20 人不產生

charityMeals/{mealId}            // vendorId, date, source: noshow | donated, status
charityReservations/{resId}      // 與 orders 分開存放，保留 30 天
charityBans/{userId}             // until
disasterEvents/{eventId}         // type, counties, dates, source
```

安全規則要點：`tasteProfiles` 僅本人可讀；`areaInsights` 僅店家可讀且只含彙總；`charity*` 不開放給店家讀取個人欄位；抽獎、兌現、開池一律由後端寫入。

## 14. 隱私與法規

上線前活動辦法、訂購條款、隱私條款須經律師審閱；以下為依公開條文整理的設計依據，非法律意見。

### 14.1 法規

- **折價券效期**：無償發行的抵用券、折價券不屬於消保法規範的商品（服務）禮券，可設使用期限，但須於領取時明示。
- **抽獎**：屬公平交易法「贈獎」，受《事業提供贈品贈獎額度辦法》規範；本系統單張券最高 100 元，遠低於最大獎項與全年總額上限。
- **截單後不可取消**：現做餐點屬易腐敗商品，通訊交易解除權應有例外適用，條款寫法待律師確認。
- **活動辦法須載明**：規則由平台訂定；券的成本由店家負擔、於店家訂單中折抵。
- **天災**：停班自動退款、天災期間等值替換配菜須事先寫入條款。
- **愛心餐**：現場自取、當日有效、取餐結束 2 小時後報廢；保存與交付的食安責任由店家負責。

### 14.2 隱私

- 店家只看得到取餐號，看不到消費者姓名以外的資料；出餐標籤不印姓名。
- 區域統計以取餐點計算、低於 20 人不顯示。
- 不儲存定位軌跡；常用地點只存粗略 geohash（約 150 公尺）。
- 愛心餐預約、領取、瀏覽紀錄不進入統計與推薦，只用於預約管理與防濫用。
- 過敏資訊只用於使用者自己的篩選。
- 隱私條款說明購買紀錄會匿名用於區域統計。
