# BunnBaa ISO 27001:2022 落差分析

日期：2026-09-21　範圍：本 repo（`web/`、`functions/`、`firestore.rules`、`firebase.json`、GitHub Actions）＋ Firebase 專案 `bunnbaa-mvp-5474`

## 結論

- **「符合」≠「認證」**。這份文件把系統的技術控制對照 ISO 27001:2022 Annex A，並修補了能靠程式碼／設定處理的缺口。要拿正式認證還需要 ISMS 管理制度（政策、風險評鑑、適用性聲明 SoA、內部稽核、管理審查）與外部稽核，這些是組織層級文件，不是程式碼能產出的（見第 4 節）。
- 技術面（Annex A.8）本次補了 6 個缺口；剩下的缺口**主要卡在兩件事**：真實的商家身分驗證（目前平台登入是 mock）、Blaze 方案（備份、Secret Manager、監控告警）。
- 圖例：✅ 已達成／🟡 部分／❌ 缺口／➖ 不適用（由雲端供應商負責或不在範圍）

## 3. 開放缺口（依優先度）

**2026-09-25 情境重新評估**：這個專案目前的定位是 AI Builder Cup 參賽用的原型，不是要正式商轉上線，之前這節的優先序是照「假設要真的上線」的規格寫的，偏重了。重新拆開來看：
- **2FA（SU 自己的 Google／GitHub 帳號）維持建議做**——理由跟這個專案值不值錢無關：比賽規則要求提交**公開 GitHub repo**＋**公開部署的網址**，評審期（10/19–11/6）這兩樣東西客觀上是公開曝露的，而且這兩組帳號是 SU 平常在用的帳號，保護它們是通用好習慣。SU 這邊已完成（2026-09-25）。
- **`ckchildlikekid@gmail.com`（Donna）開 2FA、GitHub branch protection**——標記為**待跟 Donna 討論**，不預設一定要做。branch protection 尤其會改變兩人目前的推送流程（直接推 `master` 觸發自動部署），對一個衝刺到 10/18 截止的參賽專案來說，多一道 PR 審核可能是拖慢速度而不是降風險，值不值得看討論結果。
- **API key referrer 限制維持建議做**——key 本來就公開在前端 bundle 裡，限制不是防外洩，是防別人拿去別的網域打，濫用會花到 Blaze 的真實費用（OTP 簡訊、Gemini 呼叫都要錢），這個風險對參賽專案一樣成立。
- **Cloud Audit Logs 暫緩**——它只有事後鑑識用途（查誰讀寫過什麼），不會主動擋下任何事，對一個曝光度低、三週後可能就沒人再碰的參賽專案來說，投入報酬率低，等要往正式商轉再開。

**P1　現在就能做，需要人工操作**
1. 部署 `firestore.rules`（第 1 節的規則修補要部署才生效）。**注意**：部署後 `payouts`／`accuracy_reports` 不再公開，商家儀表板需先完成下方「商家帳號綁定」才看得到資料

**商家帳號綁定（新增／變更商家 owner 的作業流程）**
1. Firebase Console → Authentication → Users → 新增商家的 email／密碼帳號，複製該帳號的 **UID**
2. Firestore Console → `vendors/{商家 id}` 文件 → 新增欄位 `owner_uid`（string）＝ 上一步的 UID
3. 商家用該帳號登入 `/lock/vendor` 即可看到自己的撥款與校準報告；換人時改 `owner_uid` 即可
